## 1. 为什么要改

说明书 4.6 那张分工表，是按模块横切的：A 拿 M01+M03，B 拿 M04+M05，C 拿 M06+M07，D 拿数据库层、M02、M08 和主框架。看上去挺均匀，实际跑起来 D 是全局瓶颈。说明书自己写的一天时间安排就暴露了这个问题——09:10 D 提交 db.c 里的接口定义，A 才能开始实现；14:30 B 开处方要查库存，又得等 D 补一个 medicine_query_stock；15:00 D 提交接口，通知 B、C 继续。三个人有一半时间在等第四个人。原因是 db.c 被设计成"所有模块的 SQL 都写在这里"，那这个文件就成了所有人的上游。

第二件事是功能量。8 个模块、9 张表、35 个左右的函数，对一个学期的课程设计来说偏薄，做出来的东西答辩时不太撑得住。所以要在不动技术栈的前提下加料——还是 Linux C、还是 MySQL 8、还是终端字符界面，只是把业务链条补得更像真实门诊一点。

第三件事是协作平台。说明书第三章整章在讲码云上传，这次要求换到 GitHub，而且合并必须走 Pull Request，不能像 4.2 那样本地 merge 完 push 上去。

## 2. 本方案的几条口径

先把口径说清楚，免得后面每一节都要重复解释。

这是本科课程项目，不是生产系统。说明书 1.6 里的性能指标（常规操作 200ms、支持 10 个并发终端、单表 10 万行查询 500ms）我们原样保留在文档里，但不作为验收项，也不做压测。演示数据量按几千行封顶，seed 脚本灌多少就是多少。真要有人问起来，回答是"课程环境下未做性能测试"，这句话会写进 README。

工期只粗排到周，不算人日、不画甘特图。因为全程 AI agent 辅助开发，写代码这一段被压缩得很厉害，估算的重心整个变了：瓶颈不再是"敲这些代码要几天"，而是"四个人对接口能不能对上"和"评审与联调要花多少轮"。所以第 10 节的里程碑只给顺序和验收方式，不给精确天数。

运行环境只要求是 Linux。不锁 Rocky Linux 9.8，也不锁 glibc 2.34。四个人的机器不一定一样，Ubuntu 22.04、Debian 12、Rocky 9 都行，只要能装上 gcc（11 上下）、make、MySQL 8 的客户端开发库（libmysqlclient-dev 或 mysql-devel）。终端界面继续用标准 ANSI 转义序列，不引入 ncurses，不做 Web 界面——这一条和说明书一致，不改。

数据库统一用 MySQL 8。为了省掉四个人各自装库的麻烦，仓库里附一份 docker-compose.yml 起一个本机 MySQL 8 容器，但这只是开发期便利，交付形态仍然是"单台 Linux + 本机 MySQL"，不依赖云服务。

排除范围这一条要特别说明，因为新增功能最容易在这里越界。我们仍然不做：收费退费、系统日志与监控告警、进程间通信与多线程、独立科室表（dept 继续是 t_doctor 的字符串字段）、系统配置界面、互联网医院、移动端、医保联网、短信通知、数据库集群。

## 4. 四人分工

### 4.1 一条贯穿始终的原则

**菜单跟角色走，表和写函数跟 owner 走。**

意思是：某个角色工作台上的页面，由负责这条线的人写；某张数据表的字段定义和"唯一写入口函数"，由这张表的 owner 写。跨角色的写操作，只能调 owner 提供的函数，不许自己拼 UPDATE 语句改别人的表。跨角色的只读查询（SELECT / JOIN）不受限制，谁需要谁自己写。

这条原则解决了纵切分工的最大隐患：医生接诊要改 t_appointment.status，开方要扣 t_medicine.stock，这两个动作分别落在患者线和管理员线的表上。如果不约定入口，四个人会在同一张表上各写一套 UPDATE，状态机和库存很快就对不上账。

### 4.2 A —— 患者线

负责模块：M01 患者档案、M03 预约挂号、M09 排班与号源，以及 M08 里的患者注册那半边。

owns 的表：t_patient、t_appointment、t_schedule。

主要文件：src/patient.c、src/appointment.c、src/schedule.c、src/ui_patient.c，头文件 include/patient.h、appointment.h、schedule.h。

对外提供的写入口（别人只能调这几个）：

```c
int patient_register(const patient_t *p, char *out_id, int idlen);
int patient_update_self(const char *pid, const patient_t *p);   /* 只允许改联系方式 */
int patient_set_status(const char *pid, int status);            /* 注销：C 在管理员菜单里调 */
int appointment_add(const appoint_t *a, int *out_appoint_id);   /* 内含占号 */
int appointment_cancel(int appoint_id, const char *op_role, const char *reason);
int appointment_reschedule(int appoint_id, const char *new_date, const char *new_slot);
int appointment_set_status(int appoint_id, int new_status, const char *reason); /* B 在 visit_take 事务内调用；爽约 UI 调 A 的 appointment_mark_noshow */
int schedule_add_week(const char *doctor_id, const char *monday, int am_quota, int pm_quota);
int schedule_set_quota(int schedule_id, int quota_total);
int schedule_take_quota(int schedule_id);    /* 条件 UPDATE，失败返回 ERR_NO_QUOTA */
int schedule_release_quota(int schedule_id);
```

排班这块放在患者线，是因为号源的消费者是挂号动作，占号、放号、改期必须在同一个事务里跟 t_appointment 一起写。管理员端也要有排班维护菜单，但那个页面由 C 写 UI，调 A 的 schedule_* 函数——原则就是这么用的。

### 4.3 B —— 医生线

负责模块：M04 就诊记录、M05 处方管理、M07 病历管理，外加处方模板。

owns 的表：t_visit_record、t_prescription、t_presc_detail、t_medical_record、t_presc_template。

主要文件：src/visit.c、src/prescription.c、src/medical_record.c、src/presc_template.c、src/ui_doctor.c。

B 这条线是事务最重的，两个跨表事务都在这儿：接诊（写 t_visit_record + 改 t_appointment.status）和开方（写处方主表 + 写明细 + 扣库存）。接诊改状态调 A 的 appointment_set_status，扣库存调 C 的 medicine_change_stock，事务的 begin/commit/rollback 由 B 自己掌握（规矩见 7.3）。

对外提供的写入口：

```c
int visit_add(const visit_t *v, int *out_visit_id);            /* 不含改预约状态，由调用方组合 */
int prescription_add(const presc_t *p, const presc_item_t *items, int n, int *out_presc_id);
int prescription_void(int presc_id, const char *reason);       /* 不回滚库存，只留痕 */
int medical_record_add(const medrec_t *r, int *out_record_id);
int medical_record_update(int record_id, const medrec_t *r);   /* 内含 24 小时锁定校验 */
int presc_template_add(const char *name, const presc_item_t *items, int n);
int presc_template_apply(int tpl_id, presc_item_t *out, int *n); /* 复制明细行，可再改数量 */
```

医生工作台首屏那段"今日待就诊预约"仍然由 appointment_query_by_doctor_today() 出，函数在 A 那边，B 只调用。

### 4.4 C —— 管理员线

负责模块：M02 医生管理、M06 药品管理、M10 库存流水与预警，以及管理员侧的各类查询与患者导出入口。

owns 的表：t_doctor、t_medicine、t_stock_log。

主要文件：src/doctor.c、src/medicine.c、src/stock_log.c、src/ui_admin.c。

管理员菜单里那些"查患者、查处方、查病历、导出患者"的页面，UI 由 C 写，数据函数调 A 和 B 的查询接口。这样管理员端加页面不需要动别人的文件。

对外提供的写入口：

```c
int doctor_add(const doctor_t *d, char *out_id, int idlen);
int doctor_update(const char *did, const doctor_t *d);
int doctor_delete(const char *did);                 /* 软删除，status=0 */
int medicine_add(const medicine_t *m, char *out_id, int idlen);
int medicine_update_price(const char *mid, double new_price);
int medicine_change_stock(const char *mid, int delta, int change_type,
                          int ref_id, const char *operator_name);
                            /* 唯一改库存的入口，内部同事务写一条 t_stock_log */
int medicine_check_stock(const char *mid, int actual_count, const char *operator_name);
                            /* 盘点：差异 = actual - stock，走 medicine_change_stock 记盘盈盘亏 */
```

medicine_change_stock 是全场最关键的一个函数。B 开方扣库存、C 自己入库出库盘点，全部走它，所以库存和流水永远对得上。它的实现靠一条带条件的 UPDATE：

```sql
UPDATE t_medicine SET stock = stock + ?      -- delta 为负即扣减
 WHERE med_id = ? AND stock + ? >= 0;
```

然后判断 mysql_affected_rows() 是不是 1，不是就返回 ERR_STOCK_LOW。这样写既避免了"先 SELECT 再 UPDATE"的竞态，也不需要任何锁或者队列——单进程终端程序，一条条件更新就够了。

### 4.5 D —— 统合线

负责模块：M08 登录与用户（除患者注册）、M11 待办提醒的公共部分、数据库层、公共层、主框架、构建与 CI、集成测试。

owns 的文件：src/db.c（libdb.so）、src/common.c（libcommon.a）、src/user.c、src/main.c、src/todo.c、Makefile、docker-compose.yml、scripts/**、.github/**、tests/harness.c。

D 不再写业务 SQL，这是和原说明书最大的区别。db.c 只提供六个东西：

```c
int  db_connect(const char *host, const char *user, const char *pass, const char *db);
void db_close(void);
int  db_exec(const char *sql, my_ulonglong *affected_rows);      /* INSERT/UPDATE/DELETE */
int  db_query(const char *sql, db_result_t **out);               /* SELECT，返回结果集句柄 */
void db_result_free(db_result_t *r);
int  db_tx_begin(void); int db_tx_commit(void); int db_tx_rollback(void);
char *db_escape(const char *src, char *dst, int dstlen);         /* 包 mysql_real_escape_string */
```

有了这层封装，A、B、C 谁都不用等 D 写接口，自己就能把 SQL 跑起来。D 的活变成：把公共层做稳、把构建和 CI 搭起来、把三条线合到一起、当冲突和接口的仲裁人。

D 还负责 M11 的公共部分——todo.c 里放三端待办的查询函数骨架和统一的打印格式，具体的 SQL 由各条线自己填（甲填 todo_patient、乙填 todo_doctor、丙填 todo_admin），因为待办读的是各自那几张表，只读、不写，不存在冲突。

主框架方面，main.c 只保留三件事：欢迎信息、身份选择、登录分发。三个角色的菜单各自放在 ui_patient.c / ui_doctor.c / ui_admin.c 里，main.c 通过一张函数指针表跳过去。这样四个人改菜单不会碰到同一个文件。

### 4.6 表与写入口归属总表

| 表 | owner | 唯一写入口 | 谁会调 |
|----|-------|-----------|--------|
| t_patient | A | patient_register / patient_update_self / patient_set_status | A 自己；C（管理员注销、改档案） |

| t_schedule | A | schedule_add_week / set_quota / take_quota / release_quota | A 自己；C（管理员维护排班，走 UI 调 A 的函数） |
| t_visit_record | B | visit_add | B |
| t_prescription / t_presc_detail | B | prescription_add / prescription_void | B |
| t_medical_record | B | medical_record_add / update | B |
| t_presc_template | B | presc_template_add / apply | B |
| t_doctor | C | doctor_add / update / delete | C；B（医生改本人电话，走 UI 调 C 的函数） |

只读跨表随意，写跨表必须走 owner 的函数。这条写在 .ai/conventions.md 里，也写在 PR 模板里，评审时第一条就看这个。

### 4.7 工作量配平

粗估：A 26%、B 27%、C 22%、D 25%。不用算太细，理由是——A 的模块数最多（M01+M03+M09）但逻辑都浅，主要是表单读写和状态校验；B 的模块数少但两个事务最烧脑子，还要处理 24 小时锁定这种时间判断；C 全是 CRUD 加流水，最规整，量也最可控，所以给 C 减一点，让 C 兼管仓库的 Issues 看板和 CHANGELOG；D 代码量不大，但 CI、构建、联调、仲裁都在他身上，而且他是唯一一个必须看懂全部代码的人，所以业务量要压到最低。

每条线配一个 AB 角：A↔B 互备，C↔D 互备。互备的要求只是"能读懂对方的代码、能在对方请假时把 PR 审掉"，不要求能重写。

## 5. 功能扩展清单

### 5.1 点数是怎么算的

按说明书各模块"主要函数"那一行数功能点：M01 六个（含导出）、M02 五个、M03 五个、M04 三个、M05 四个、M06 六个（含盘点）、M07 三个、M08 三个，合计 **35 点**。

本次新增 **12 点**，总计 47 点，增幅 **34.3%**。按模块数算是 8 → 11，增幅 37.5%。两个口径都落在 30%–40% 区间里。明细见附录 B。

### 5.2 新增模块

**M09 排班与号源（4 点，owner A）**

新表 t_schedule：doctor_id、work_date、time_slot（上午/下午）、quota_total、quota_used、status。

功能：schedule_add_week 按周批量生成某医生的排班（一次 INSERT 七天，遇到已存在的日期跳过）；schedule_query_by_doctor 查某医生一周的排班和余号；schedule_set_quota 调整某个半天的号源数；挂号时占号、取消时放号、改期时先放后占。

原来的规则"同一患者同一天同一医生不能重复挂号"保留，在它之上多一层余号校验。患者挂号时看到的医生列表，从"所有在职医生"变成"该日期该时段还有余号的医生"，后面括注余号数，例如 `D001 张医生 内科 主任医师 [余 3]`。

**M10 库存流水与预警（3 点，owner C）**

新表 t_stock_log：log_id、med_id、change_type（1 入库 / 2 出库 / 3 处方扣减 / 4 盘盈 / 5 盘亏 / 6 作废留痕）、quantity、before_stock、after_stock、ref_id（关联处方号或盘点批次）、operator、remark、create_time。

功能：medicine_change_stock 内部每次变动写一条流水（这是内嵌的，不额外暴露接口）；medicine_query_stock_log 按药品查流水，支持按时间段过滤；medicine_query_low_stock 列出库存低于 LOW_STOCK 的药品清单。

盘点从"直接改 stock"改成"输入实盘数，系统算差异并生成一条盘盈或盘亏流水"，这样库存对不上的时候能查是哪一次动的。处方作废仍然不回滚库存（说明书原有规则，不改），但会在流水里补一条 change_type=6 的记录，remark 写清处方号，方便对账。

**M11 三端待办提醒（3 点，owner D 提供框架，三条线各填自己的 SQL）**

医生登录后首屏：今日待接诊 N 人、有 N 条就诊记录还没写病历、N 条病历在 24 小时可修改窗口内（附剩余小时数）。
患者登录后首屏：N 条未就诊预约（附"还剩 N 天"）、上次就诊的处方和病历是否已生成。
管理员登录后首屏：N 种药品库存不足、今日挂号 N 条、N 个医生账号处于离职状态、N 个患者账号处于注销状态。

实现上就是几条 COUNT 加 JOIN，日期差用 MySQL 的 DATEDIFF 和 TIMESTAMPDIFF，或者在 C 里 (t2 - t1) / 86400。没有报表、没有图表、没有导出。

### 5.3 既有模块增强（2 点）

**预约改期与爽约（1 点，A）**：appointment_reschedule 仅允许已登录患者修改本人预约、管理员修改任意预约，医生不得改期；在一个事务里先释放旧号源、再占用新号源、最后更新日期时段，保留原 appoint_id 和挂号时间，另加 change_time 和 change_count 记录改期。新增 3 爽约，仅管理员或该预约的归属医生可标记日期早于今天且 status=0 的预约；UI 调 A 的 appointment_mark_noshow，由其在事务内调用 appointment_set_status，号源不释放。具体规则以 SRS 第 6.1 节和附录 D 为准。

**处方模板（1 点，B）**：新表 t_presc_template（tpl_id、tpl_name、doctor_id、create_time）和 t_presc_template_item（引用模板、med_id、quantity、dosage）。医生把常用组合存成模板，开方时选一个模板一键带入明细，再逐条改数量。实现就是把模板明细行复制到开方的临时数组里，纯 CRUD。

### 5.4 顺手做掉、不计入点数的小改动

这几项改动量很小（每项十几行到几十行），做完能明显提升可用性，所以不单独算点：

- 患者、药品、医生列表加模糊查询和分页（WHERE name LIKE ? + LIMIT ? OFFSET ?）
- 病历打印视图：把一次就诊的主诉、体检、诊断、处方明细、病史按固定格式排到终端，也可以重定向到文本文件
- 登录失败计数落库（fail_count + lock_until），配合 5 次锁 10 分钟
- 会话超时：15 分钟无输入自动退回登录界面，用 time() 比较
- 患者导出支持选择字段，输出 CSV（仍然只有一个导出功能，不新增报表种类）
- t_medicine 加 status 字段（1 在售 / 0 停用）。停用的药不出现在开方选择列表里，但历史处方明细仍能正常显示

如果老师把这些也算进增幅，比例会到 45% 左右，超出区间。那种情况下先砍"病历打印视图"和"导出可选字段"两项，正好回到 40% 以内。

### 5.5 为什么这些都不需要复杂算法

这一条是硬约束，逐项对照：

| 功能 | 实现手段 | 涉及的"算法" |
|------|----------|-------------|
| 号源校验与占用 | 一条带条件的 UPDATE，看 affected_rows | 无 |
| 排班按周生成 | 循环七次 INSERT，重复日期跳过 | 循环 |
| 待办计数 | COUNT + JOIN，DATEDIFF / TIMESTAMPDIFF | SQL 聚合 |
| 库存流水 | 每次变动多插一行，查询按 med_id 和时间过滤 | 无 |
| 低库存清单 | WHERE stock < LOW_STOCK ORDER BY stock | 排序交给 MySQL |
| 盘点差异 | actual - stock，正负决定盘盈盘亏 | 一次减法 |
| 处方模板 | 复制明细行到数组 | 数组拷贝 |
| 预约改期 | 一个事务里：放旧号 → 占新号 → 更新字段 | 无 |
| 分页 | LIMIT / OFFSET | 无 |
| 会话超时 | time() 相减比阈值 | 一次减法 |
| 病历 24 小时锁定 | TIMESTAMPDIFF(HOUR, ...) <= 24 | 一次减法 |

没有排序算法要自己写，没有调度或排班优化，没有推荐，没有并发控制算法（单进程终端程序，靠事务和条件更新），没有加解密（密码按说明书保持明文，hash_password() 仍留空桩；真要启用哈希就直接链 OpenSSL 的 SHA256()，不自己实现）。所有新增功能的难度都在"把 SQL 写对、把事务边界划对"这一层，属于课程项目该有的难度。

### 5.6 明确不做的

为了防止做到一半范围膨胀，下面这些即使有人提议也不做：收费退费、医保、短信或微信通知、Web 或移动端界面、多线程或多进程、独立科室表、库存阈值可配置、通用操作审计日志、数据可视化图表、药品说明书知识库、智能分诊或推荐医生。有想法写进 backlog 标签的 Issue，不进 v1.1。

### 6.2 既有表加字段

| 表 | 新增字段 | 用途 |
|----|---------|------|
| t_appointment | schedule_id INT NULL | 关联占用的号源，改期时用来放号 |

### 6.3 说明书里两处小坑，顺手补掉

第一，t_medical_record.update_time 建表时只有 `DEFAULT CURRENT_TIMESTAMP`，没有 `ON UPDATE CURRENT_TIMESTAMP`。而 M07 的规则是"医生仅能修改本人书写且在 24 小时内的病历"，判断依据就是这个字段。如果不加 ON UPDATE，或者更新时不手动 set update_time = NOW()，那这个 24 小时窗口永远是按创建时间算的。我们两个都做：建表加 ON UPDATE，更新语句里也显式写 NOW()，双保险。

第二，t_medicine 原来没有 status 字段，但 M06 有 medicine_add / medicine_delete。药品被 t_presc_detail 引用，物理删除会让历史处方的药品信息查不出来。所以补一个 status 做软删除，和说明书 1.1.4 里"软删除"的术语定义一致。

另外说明书的 9 张表都没有声明外键。我们也不加物理外键——加了以后软删除和作废会到处报错，课程项目里得不偿失。取而代之的是一个数据一致性检查脚本 scripts/check_data.sql，跑几条 SELECT 找孤儿数据（明细里的 med_id 不在药品表、就诊记录里的 appoint_id 不存在、status=1 的预约对应的医生已离职等），make check-data 时执行，答辩前跑一遍。

### 6.4 脚本

- `scripts/ddl/*.sql`：每张表一个文件，谁的表谁写，避免四个人改同一个 SQL 文件产生冲突
- `scripts/init_db.sql`：按固定顺序 source ddl 目录下的文件，建库建表并预置 admin/123456
- `scripts/migrate_v1.1.sql`：老库升级用，幂等（先查 information_schema 再 ALTER），已经建过 v1.0 库的机器不用重建
- `scripts/seed_demo.sql`：演示数据。10 个患者、4 个医生、30 种药、一周排班、20 条历史就诊与处方
- `scripts/seed_test.sql`：测试数据，灌到独立的 medical_test 库，make test 结束后 DROP
- `scripts/demo.sh`：一条命令走完"注册 → 挂号 → 接诊 → 开方 → 写病历 → 患者查询"的全流程，作为每个里程碑的验收方式

## 7. 接口约定

### 7.1 第 0 天要定稿的东西

四个人第一次开会就把 include/ 下所有头文件写完并合并进 main，包括结构体定义、函数签名、错误码。之后接口改动由 owner 与 D 确认并通知受影响成员，不要求全员 approve 或额外审批门禁。头文件是这套分工里唯一的强耦合点，把它冻结住，剩下的冲突都是局部的。

| 头文件 | owner |
|--------|-------|
| common.h（结构体、常量、输入输出工具） | D |
| errcode.h | D |
| db.h | D |
| ui.h（清屏、表格对齐、菜单打印工具） | D |
| patient.h、appointment.h、schedule.h | A |
| visit.h、prescription.h、presc_template.h、medical_record.h | B |
| doctor.h、medicine.h、stock_log.h | C |

### 7.2 统一错误码

沿用说明书原有的 ERR_DB_CONN、ERR_DB_EXEC、ERR_DUPLICATE，补齐：

```
ERR_PARAM        参数非法（空指针、负数、超长）
ERR_NOT_FOUND    记录不存在
ERR_BAD_STATE    状态不允许（例如对已就诊的预约执行取消）
ERR_PERM         越权（患者查别人的档案）
ERR_NO_QUOTA     号源已满
ERR_STOCK_LOW    库存不足
ERR_LOCKED       账号锁定中 / 病历超 24 小时锁定
ERR_TIMEOUT      会话超时
ERR_TX           事务失败已回滚
```

全部在 errcode.h 里定义成负的枚举值，配一个 `const char *err_str(int code)` 返回中文描述。业务函数一律返回 0 表示成功、负值表示错误码，出参通过指针带出来。UI 层拿到错误码统一打印，不在业务函数里 printf。

### 7.3 事务规矩（最容易翻车的一条）

**只有发起业务动作的那个人调 db_tx_begin / commit / rollback，被调用的 owner 函数内部绝不自己提交或回滚，只返回错误码。**

以开方为例，B 的 prescription_add 内部是这样的：

```
db_tx_begin()
  INSERT t_prescription              → 拿 presc_id
  循环 INSERT t_presc_detail         → 任一条失败就 goto rollback
  循环 C 的 medicine_change_stock()  → 返回 ERR_STOCK_LOW 就 goto rollback
db_tx_commit()
rollback: db_tx_rollback(); return ERR_TX;
```

medicine_change_stock 内部只执行那条条件 UPDATE 和一条 INSERT 流水，不碰事务控制。接诊同理，B 的 visit_take 开启事务，先调 visit_add 写就诊记录，再调 A 的 appointment_set_status 置已就诊，不释放号源。

取消由患者或管理员 UI 调 A 的 appointment_cancel，由它开启事务；appointment_set_status 在成功置 2 后释放一次号源，外层不得重复释放。上述预约写入口在函数内校验当前会话、角色和归属；爽约还须校验日期早于今天。appointment_set_status 内部不控制事务，任一步失败交由外层回滚。详见 SRS 第 3.3、4.4、7.2 节和附录 D。

如果这条不写死，两个人各写一半事务，MySQL 的隐式提交会把事务切碎，出问题的时候完全查不出来。

### 7.4 UI 与业务分层

ui_*.c 只负责清屏、打印、读输入、表格对齐；业务函数不 printf、不 scanf、不 exit。所有输入统一走 common.c 里的 read_line / read_int / read_decimal / read_date，内部用 fgets 定长读取、去掉换行、非法输入就地重试而不是让程序崩掉。这一层看起来是杂活，但它是四个人代码风格能不能统一的决定因素，也是测试能不能脱离终端跑起来的前提。

### 7.5 三个减少冲突的写法约定

- **Makefile 用通配符**：`SRCS = $(wildcard src/*.c)`，新增文件不需要改 Makefile，四个人加自己的 .c 不会冲突
- **main.c 不放菜单文字**：角色菜单在各自的 ui_*.c 里，main.c 只有一张跳转表，改菜单不碰 main.c
- **DDL 按表分文件**：见 6.4，避免四个人同时改 init_db.sql

再加一条纪律：每个 .c 文件只有一个 owner，PR 里出现别人 owns 的文件，必须在描述里 @ 到本人并说明原因。

## 8. Git 与 GitHub 协作

### 8.1 分支与命名

当前课程项目只用 main 作为集成主线；feature/* 和 hotfix/* 从 main 切出，通过 PR 合回 main。可交付版本在实际验收后打 tag，不另建集成或发布分支，不新增分支保护、固定审批人数或 required status checks 门禁。

命名换成能一眼看出是谁的哪个模块：

```
feature/patient-m09-schedule      A
feature/doctor-m05-template       B
feature/admin-m10-stocklog        C
feature/core-ci                   D
hotfix/login-lock
```

### 8.2 PR 规则

1. 一个 PR 只做一件事，对应一个 Issue，描述里写 `Fixes #12`
2. 单个 PR 的 diff 控制在 400 行以内。这一条在 AI 辅助开发下最容易被违反——agent 一次能给你生成八百行，看起来都挺对，但没人审得动。宁可拆成三个 PR
3. 标题用 conventional commits：`feat(M09): 排班按周生成与余号校验`、`fix(M05): 明细插入失败时未回滚库存`
4. 描述固定四段：改了什么 / 怎么测的 / 影响谁的接口 / AI 辅助说明
5. 按第 8.3 节交叉评审，不要求固定 approve 数量
6. 公共接口及核心文件改动与 D 确认，不增加 GitHub 审批门禁
7. 不许合并自己的 PR
8. 不改写 main 历史；个人 feature 分支 rebase 之后可以用 `--force-with-lease`，不要用裸 `--force`

### 8.3 评审交叉

A 和 B 互审，C 和 D 互审，核心文件（第 6 条那些）D 必审。这样 D 不会变成所有 PR 的必经节点，也保证每条线的代码至少有第二个人读过。

说明书 4.4 的代码审查清单继续用，再加三条针对 AI 生成代码的检查项：有没有 sprintf / strcpy / strcat（应一律换成 snprintf 和 strncpy 并显式截断）；mysql_query 的返回值有没有判；malloc 之后有没有对应的 free，所有错误分支上是否都释放了。

### 8.4 GitHub 协作工具

- **仓库设置**：沿用现状，本轮文档澄清不新增分支保护、审批人数或 required status checks 配置
- **CODEOWNERS**：可选的负责人提醒，文件归属见 SRS 第 11.2 节；不要求新增该文件或强制 owner review
- **PR 模板** `.github/pull_request_template.md`：四段式，最后一段是"AI 辅助说明（用了哪个 agent、生成了哪部分、人工改了哪部分）"
- **Issue 模板**：bug 和 feature 两种，feature 模板里要求写清属于哪个模块、谁是 owner、涉及哪张表
- **Issues 当任务板**：47 个功能点一人建自己那部分，打 module/M01–M11 和 owner/A–D 标签
- **Projects 看板**：四列——待办、进行中、待评审、已完成
- **Milestones**：对应 W1–W4
- **Actions**：`.github/workflows/ci.yml`

### 8.5 CI 内容

runner 用 ubuntu-latest，services 起一个 mysql:8 容器（MYSQL_DATABASE=medical_test，root 密码固定），步骤：

GitHub 在校园网环境下不一定稳。仓库保留 gitee 作为第二个 remote，`git push origin` 之后再 `git push gitee`，两边同步；克隆失败时用镜像地址或者代理。CI 只在 GitHub 上跑。这一条纯粹是保底措施，不影响流程设计。

### 8.7 AI 辅助开发的署名口径

课程项目，这部分要交代清楚，不能含糊。约定：PR 描述里固定写一段 AI 辅助说明，讲清哪个 agent、生成了哪部分、人工改了哪部分、为什么这么改。CHANGELOG 里每个版本也带一段总的说明。答辩时每个人要能逐行讲清自己那条线的代码——讲不清的部分，就是没吃透的部分，评审时会被问。

## 9. AI agent 辅助开发的做法

### 9.1 人干什么，agent 干什么

人负责：定接口、判业务规则是否合理、划事务边界、评审别人的 PR、跑演示、写文档里"为什么这么设计"的部分。

agent 负责：生成样板代码（SQL 拼装、错误分支、菜单打印、表格对齐）、写单元测试骨架、写 migrate 脚本、按头文件生成结构体和函数框架、读一段 diff 挑毛病、补文件头注释。

分工的界线是"需要判断的地方归人，需要重复的地方归 agent"。

### 9.2 统一上下文

仓库里放一个 `.ai/` 目录，四个人喂给 agent 的上下文一致，产出风格才一致：

- `.ai/style.md`：编码规范（4 空格缩进、函数不超过 80 行、命名 模块_动作、错误码返回约定）
- `.ai/schema.md`：13 张表的完整 DDL
- `.ai/conventions.md`：分层规矩、事务规矩、跨表写入口清单
- `.ai/prompt-patient.md` / `-doctor.md` / `-admin.md` / `-core.md`：各条线的任务模板

每次让 agent 写代码，把对应的头文件、schema.md 和 conventions.md 一起给它。不给 conventions.md 的话，agent 一定会自己拼 UPDATE 改别人的表。

### 9.3 三道闸

1. `make` 带 `-Wall -Werror`，零警告
2. `make asan` 用 `-fsanitize=address,undefined` 重编，跑一遍 demo.sh，无泄漏无越界
3. `make lint` 跑 grep 禁词检查

三道闸在本地和 CI 都跑，过不了不提 PR。这三条能挡掉 AI 生成代码里八成以上的问题——剩下的两成是业务逻辑错，只能靠人审和测试用例。

### 9.4 代码不要一股 AI 味

这一条也是要求。具体做法：

- 注释写"为什么"，不复述代码。`/* 扣减库存：用条件更新避免先查后改的竞态 */` 是有用的，`/* 调用函数更新库存 */` 是废话
- 不要每个函数都套 `@param` `@return` 模板。文件头注释按说明书 1.6 的要求写（文件名、功能、作者、创建日期），保持三行以内
- 错误处理不许一律 `return -1`，要返回具体错误码
- 变量名跟着说明书的命名习惯走，不要让 agent 起 `tempData2`、`resultFinal` 这种名字
- `.clang-format` 进仓库，`make format` 一键格式化，四个人的缩进和换行统一
- 不要让 agent 生成大段的"以下是本模块的完整实现"式注释和分隔线

## 12. 风险与应对

| 风险 | 触发场景 | 应对 |
|------|---------|------|

| PR 过大审不动 | agent 一次生成八百行 | 400 行上限，超了就拆 |
| 有人请假或掉线 | 一条线停摆 | AB 角互备 + Issues 看板进度可见 + 每日一条群消息（昨天合了什么/今天做什么/被谁卡住） |
| GitHub 访问不稳 | push/clone 失败 | gitee 镜像 remote |
| 范围膨胀 | 做到一半又想加功能 | 12 点封顶，新想法一律进 backlog 标签，不进 v1.1 |

## 附录 C：一次完整就诊在 v1.1 下的数据流

```
1  患者注册        patient_register            t_patient
2  查排班余号      schedule_query_by_doctor    t_schedule（只读）
3  挂号            appointment_add
                   ├ schedule_take_quota       t_schedule.quota_used +1（条件更新）
                   └ INSERT 预约               t_appointment（status=0, schedule_id=X）
4  医生接诊        visit_add 事务
                   ├ INSERT 就诊记录           t_visit_record
                   └ appointment_set_status(1) t_appointment
5  开处方          prescription_add 事务
                   ├ INSERT 处方主表           t_prescription
                   ├ INSERT 明细 × N           t_presc_detail（unit_price 为开方时快照）
                   └ medicine_change_stock(-N) t_medicine.stock 扣减 + t_stock_log 流水
6  写病历          medical_record_add          t_medical_record
7  患者查询        只读                        以上各表 + todo_patient 首屏提示
```

改期时第 3 步变成：schedule_release_quota(旧) → schedule_take_quota(新) → UPDATE 预约日期时段，三步一个事务。爽约由管理员或归属医生对过去日期的待就诊预约调用 A 的 appointment_mark_noshow，再由它调用 appointment_set_status(3)，不生成就诊记录、不释放号源。
